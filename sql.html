Sheet 00

Before you start

Tables, keys and the one sentence the whole language is built around. Nothing here is SQL you have to write yet.

The one thing

A database is tables, and tables are joined by holding the same value in two places.

Everything SQLBolt teaches from lesson 6 onward depends on that second half. If the idea that a relationship is just two columns agreeing is not solid, joins arrive as syntax to memorise rather than as something obvious.

What a database is, in the only sense that matters here

A is a set of tables. A table is a grid. Each row is one of the things the table is about — one film, one city, one employee. Each column is one fact recorded about every one of them, and a column holds one type of value all the way down: Year holds whole numbers in every row or it holds text in every row, never a mixture.

That is the whole model. Everything else is a consequence of it.

The three words
  • Table — one kind of thing. movies is a table; every row in it is a film.
  • Row — one of them. Also called a record.
  • Column — one fact about all of them. Also called a field.

What makes it relational

Tables would be filing cabinets if that were all. What makes the model relational is that a row in one table can point at a row in another.

The is the column whose value is different in every row, so naming the value names exactly one row. In the practice tables, movies.Id is the primary key: there is one film with Id 5, and there will never be a second.

A is a column in some other table holding those same values. boxoffice.Movie_id holds numbers that mean nothing on their own and everything the moment you read them as movies.Id. That pair of columns is the relationship, and it is the only thing joining the two tables.

Worth being clear about

The relationship is not stored anywhere as a line or an arrow. It exists because two columns hold the same values and somebody knows that. Working out which columns those are, in a database nobody has documented, is a large part of the actual job.

What SQL is

is the language you type at a database to get an answer out of it, or to change what is in it. It is declarative: you describe the result you want, and the database works out how to produce it. You never write the loop.

Statements fall into two families, and it is worth knowing which one you are in because the second can destroy things:

FamilyWhat it does
SELECT. Asks a question and gets a table back. Changes nothing. Almost all of a business analyst's SQL is this, and it is the safe half of the language.
Everything elseINSERT, UPDATE, DELETE change the data; CREATE, ALTER, DROP change the tables themselves. SQLBolt covers these last, in lessons 13 to 18.

The one sentence that runs everything

Every query you write for the next several lessons is this sentence with different words in it:

The shape

SELECT  which columns  FROM  which table;

Everything SQLBolt adds after lesson 1 — conditions, sorting, joining a second table, grouping — is another clause bolted onto that sentence in a fixed position. There is no second sentence to learn.

Why this is the first thing on the list

A business analyst is not usually asked to build the database. They are asked how many, how often, which of them, and whether the number in the report can be trusted. Answering those without SQL means asking someone else and waiting. It is also the entry requirement that appears in almost every junior data or analysis advert, and the one that is checked, often by being made to write a join at interview.

How to use these sheets
  • Read the sheet, then do that lesson's exercises in the box on the sheet. Nothing is submitted anywhere — the answer is checked by running it and comparing the table it produces against the table the answer produces.
  • The lab is the same engine with no task attached, loaded with the same tables. Use it to try things that no exercise asked for.
  • The tables are SQLBolt's, so an exercise from the site can be pasted straight in.

Sheet 01 · SQLBolt lesson 1

SELECT queries 101

Two clauses, and every query you write for the rest of the course is these two with more bolted on.

The one thing

SELECT chooses columns. It cannot choose rows.

A lesson-1 query always returns every row the table holds; the only thing you control is which columns come back and in what order. Cutting rows is WHERE, and that is the next sheet.

The shape

A names the columns you want and the table to take them from.

The form

SELECT column, another_column, …
FROM table_name;

The comes back as a table of its own, with one column for each one you asked for and one row for each row in the source table. Ask for two columns and you get two columns, in the order you named them — not in the order the table stores them.

Asking for everything

An asterisk means every column, in the table's own order.

The form

SELECT *
FROM table_name;

It is the fastest way to see what a table you have never met contains, and it is the first thing to type against an unfamiliar database. It is also the thing to stop doing the moment you know what you want: naming your columns says what the query is for, and survives someone adding a column next month.

The parts, named

PartWhat it is
A word the language reserves: SELECT, FROM. Written in capitals by convention. The database does not care — select runs identically — but every example you will ever read uses capitals, so read them as signposts.
A keyword and what belongs to it. SELECT Title, Year is the select clause; FROM movies is the from clause. Clauses go in a fixed order, and lessons 2 to 12 are almost entirely about adding more of them.
The whole instruction, ended with a semicolon. The semicolon is what separates one statement from the next; with a single query in the box most engines will forgive you leaving it off, and it is a bad habit to build.
A name you did not invent — a table or a column. movies, Length_minutes. Case does not matter in SQLite, so title and Title both work.

Layout

SQL ignores line breaks and extra spaces, so a query can be written on one line or on five. Put each clause on its own line as soon as there is more than one: by lesson 11 a query has five clauses in it, and a wall of text is where mistakes hide.

Two that get confused

SELECT picks columns. It cuts the table vertically — fewer columns, same number of rows. Cutting it horizontally, to fewer rows, is WHERE, and that is the next sheet. Lesson 1 has no way to return fewer rows than the table holds.

Sheet 02 · SQLBolt lessons 2 and 3

Constraints

WHERE, and the operators that go in it — comparison, ranges, lists, patterns, and how to combine them without getting the precedence wrong.

Cutting rows

Lesson 1 could only choose columns. chooses rows: it is tested once against every row in the table, and the row survives if the test comes back true.

The form

SELECT column, another_column
FROM table
WHERE condition;

WHERE always comes after FROM. Every clause in SQL has a fixed position, and getting them out of order is a syntax error rather than a different result.

Testing numbers

OperatorWhat it asks
=   !=   <>Equal, not equal. != and <> are the same thing; one equals sign, not two — SQL is not most programming languages here.
<   <=   >   >=Less than, and so on. Ordinary.
Within a range, including both ends. BETWEEN 2 AND 5 matches 2 and matches 5.
NOT BETWEEN … AND …Outside that range, excluding both ends.
Matches any value in the list. Shorter than a row of ORs and easier to read.
NOT IN (…)Matches none of them.
The one that catches people

BETWEEN is inclusive. Asking for films BETWEEN 2000 AND 2010 gives you 2000 and 2010 as well as everything between. If you meant to exclude them, say > 2000 AND < 2010 and mean it.

Testing text

Everything above works on text too — text sorts alphabetically, so < and BETWEEN are meaningful on it. Two operators exist only for text:

OperatorWhat it asks
Matches a pattern. Case-insensitive in SQLite and MySQL, case-sensitive in PostgreSQL — a real difference between engines, worth checking before you trust a result.
%Inside a LIKE pattern, stands for any run of characters, including none. LIKE 'Toy%' catches Toy Story and Toy Story 2.
_Stands for exactly one character. LIKE 'Cars_' catches Cars 2 but not Cars.

Text values go in single quotes. Double quotes mean an identifier — a column or table name — in standard SQL, so WHERE Title = "Cars" is asking whether the Title column equals a column called Cars, and the error message you get will not say that.

Combining tests

AND requires both, OR requires either, NOT inverts what follows. AND binds tighter than OR, exactly as × binds tighter than +, so

Two readings of one line

WHERE Year > 2000 OR Director = 'Brad Bird' AND Year < 1999

means after 2000, or (Brad Bird and before 1999). If you meant the other one, brackets are not optional. Use them anywhere the answer is not obvious at a glance, which is most places.

Sheet 03 · SQLBolt lessons 4 and 5

Filtering and sorting

DISTINCT, ORDER BY, LIMIT and OFFSET. The point at which a query has its full shape.

Removing duplicates

A query returns one row per row in the table, so asking for Director from fourteen films gives fourteen directors, most of them repeats. discards duplicates across the whole selected row, not per column.

The form

SELECT DISTINCT column, another_column
FROM table
WHERE condition;

Two things that look the same

SELECT DISTINCT Director, Year does not give you distinct directors. It gives you distinct director-and-year pairs, which is a longer list. If you want one row per director, that is GROUP BY, and it is on sheet 07.

Sorting

Without a result has no guaranteed order. It will usually come back in insertion order and that is a coincidence of how the engine happened to read the table, not a promise. If the order matters, say so.

The form

SELECT column
FROM table
WHERE condition
ORDER BY column ASC/DESC;

ASC is ascending and is the default, so it is usually left off; DESC is descending and never is. Sorting text sorts alphabetically — and in most engines that means uppercase before lowercase, so 'Zebra' sorts before 'apple' unless you fold the case first.

Sort by more than one column with a comma. ORDER BY Director, Year sorts by director, and breaks ties by year.

Taking a slice

caps how many rows come back. OFFSET skips that many first. Together they are how every "page 2 of 40" on the internet is built.

The form

SELECT column
FROM table
ORDER BY column
LIMIT number OFFSET number;

Why the order matters

LIMIT is applied last, after the sort. So ORDER BY Year DESC LIMIT 5 gives the five newest — the sort happens first and the limit takes the top of it. Without an ORDER BY, LIMIT 5 gives you five arbitrary rows, and it will look stable right up until the day it is not.

The shape so far

Four sheets in, the sentence has grown to its full query form. Everything after this adds clauses in the middle rather than changing the frame:

Every clause you have met, in order
  • SELECT — which columns
  • FROM — which table
  • WHERE — which rows
  • ORDER BY — in what order
  • LIMIT / OFFSET — how many, from where

Sheet 04 · SQLBolt lesson 6

Joins

INNER JOIN: reading two tables as one, on the value they share.

Why the data is in two tables

Storing every fact about a film in one wide table means repeating the director's name on every row that mentions him, and it means an inconsistency becomes possible the moment two rows disagree. Splitting the data so each fact lives in exactly one place is , and it is why a real database has forty tables rather than one.

The cost is that answering a question now needs two of them at once. That is what a join is for.

INNER JOIN

A reads two tables as one wider table, matching rows by a value they share.

The form

SELECT column, another_column
FROM mytable
INNER JOIN another_table
    ON mytable.id = another_table.id
WHERE condition;

Read it as an instruction: take every row of the first table, find the rows of the second where the ON condition holds, and emit one combined row for each match. JOIN on its own means INNER JOIN in every engine you will meet.

The word inner is doing real work. A row with no match is dropped, from either table. So an inner join can return fewer rows than either table holds — and quietly, with nothing to tell you rows went missing. Sheet 05 is about what to do instead.

Saying which table you mean

Once two tables are in play, a bare column name is ambiguous if both have one by that name. Qualify it with the table: movies.Id, boxoffice.Movie_id. Most engines only complain when the name really is ambiguous, but qualifying everything in a join is the habit worth having — a query that reads clearly at a glance is a query you can be trusted to have checked.

Table keep that from becoming unreadable:

The same query, aliased

SELECT m.Title, b.Rating
FROM movies m
    JOIN boxoffice b ON b.Movie_id = m.Id;

AS is allowed and optional — FROM movies AS m is the same thing. Once a table is aliased, the alias replaces the name for the rest of the query; movies.Title is then an error.

Two joins that look alike

says how the tables are matched. WHERE says which of the resulting rows you keep. On an inner join they happen to behave the same and you can put a condition in either; on an outer join they emphatically do not, which is the next sheet.

What comes back

The joined result is a table like any other, so everything from sheets 01 to 03 applies to it unchanged — you can select particular columns from it, filter it, sort it, limit it. Nothing you have learned stops working because there are now two tables underneath.

Sheet 05 · SQLBolt lessons 7 and 8

Outer joins and NULLs

LEFT, RIGHT and FULL JOIN, and what NULL does to every condition you write near it.

Keeping the rows that do not match

An inner join drops any row without a partner. Often that is exactly wrong: the buildings with nobody in them are the interesting ones, and the customers who ordered nothing are the question. An outer join keeps them.

JoinWhat it keeps
Only rows with a match on both sides.
Every row of the first table, matched or not, plus the matches from the second.
RIGHT JOINEvery row of the second table, plus matches from the first. The mirror image of a left join, and rarer — most people swap the tables round and write a left join, which reads better.
FULL JOINEvery row of both. Not supported everywhere; SQLite gained it late and MySQL still has not.
The form

SELECT column, another_column
FROM mytable
LEFT/RIGHT/FULL JOIN another_table
    ON mytable.id = another_table.matching_id
WHERE condition;

OUTER is optional and means nothing: LEFT JOIN and LEFT OUTER JOIN are the same statement.

What the unmatched rows contain

A left-joined row with no partner still has to fill in the second table's columns. It fills them with NULL. So the price of an outer join is that your result now contains holes, and everything downstream has to expect them.

NULL is not a value

It is the absence of one. That has one consequence that catches everybody: NULL is not equal to anything, including NULL. So WHERE Building = NULL matches nothing at all — not even the rows where Building is null. It is not an error and there is no warning; the query returns zero rows and looks like a fact about your data.

The only way to test it
  • WHERE column IS NULL
  • WHERE column IS NOT NULL

The same applies to comparisons. WHERE Years_employed > 3 excludes the rows where that column is null, because unknown > 3 is not true — it is unknown, which is not true enough to keep the row. A filter can therefore silently drop rows you were counting.

ON versus WHERE, now that it matters

On an outer join these do different things. LEFT JOIN employees ON ... AND role = 'Artist' keeps every building and only attaches artists. LEFT JOIN employees ON ... WHERE role = 'Artist' filters the finished result, throws away every row where role is null, and quietly turns your outer join back into an inner one.

The other way out

Nulls can also be designed away. A column that defaults to 0 or '' instead of null needs no special handling anywhere downstream. That is a decision made when the table is created, and it is a real trade: a zero that means none and a zero that means we never asked are different facts, and merging them loses information you cannot get back.

Sheet 06 · SQLBolt lesson 9

Expressions

Arithmetic and functions in the SELECT clause, and naming the result with AS.

A column does not have to be a column

Anything you can compute from a row can go in the SELECT list. Arithmetic, string handling, comparisons, function calls — the result is a column in the output that exists nowhere in the table.

The form

SELECT particle_speed / 2.0 AS half_speed
FROM physics_data
WHERE ABS(particle_position) * 10.0 > 500;

Expressions work in WHERE too, and in ORDER BY. The one thing to know is that the engine computes them once per row, so an expression on a column that is indexed usually throws that index away and makes the query slower. That matters on a million rows and not at all on fourteen.

Arithmetic, and one trap in it

+ - * / and % for remainder. The trap is division: in SQLite, MySQL and SQL Server, an integer divided by an integer gives an integer, with the remainder thrown away. 7 / 2 is 3. Writing 7 / 2.0, or casting one side, gets you 3.5. This is the single most common wrong number in a hand-written report.

Functions worth knowing on day one

FunctionWhat it does
ROUND(x, n)Rounds to n decimal places. The thing you want around every average you ever show anybody.
ABS(x)Drops the sign.
LENGTH(s)How many characters. LEN in SQL Server.
UPPER(s)   LOWER(s)Case. Useful for comparing text whose case you do not trust.
s1 || s2Sticks two pieces of text together. SQLite and Postgres; MySQL wants CONCAT(s1, s2). One of the places the engines genuinely differ.

Naming what comes back

An unnamed expression gets whatever column heading the engine feels like, which is usually the expression itself. AS gives it a name.

Both kinds of alias

SELECT col AS better_name, ...
FROM a_long_widgets_table_name AS mywidgets
INNER JOIN widget_sales ON mywidgets.id = widget_sales.widget_id;

A column alias renames a column in the output; a table alias renames a table for the rest of the query. Both may drop the word AS. A column alias is not usable in the same query's WHERE — the alias does not exist yet at that point, which is sheet 08's subject — but it is usable in ORDER BY.

Sheet 07 · SQLBolt lessons 10 and 11

Aggregates

COUNT, SUM, AVG, MIN and MAX, then GROUP BY and HAVING — the first thing that changes how many rows come back.

One row out of many

Every query so far has returned one row per row in the table. An function does the opposite: it takes a whole set of rows and returns a single value about them. It is the first thing you have met that changes how many rows come back.

The form

SELECT AGG_FUNC(column_or_expression) AS aggregate_description
FROM mytable
WHERE constraint_expression;

FunctionWhat it returns
COUNT(*)How many rows. Counts every row including ones full of nulls.
COUNT(column)How many rows have a non-null value in that column. Not the same number as COUNT(*), and the gap between them is a useful data-quality check on its own.
MIN(column)   MAX(column)Smallest and largest. Work on text too.
AVG(column)The mean. Ignores nulls entirely, so an average over a column that is half empty is an average of the half that is there.
SUM(column)The total.

Grouping

Aggregating the whole table gives one number. aggregates once per distinct value of a column instead, and gives you one row per group.

The form

SELECT AGG_FUNC(column_or_expression) AS aggregate_description
FROM mytable
WHERE constraint_expression
GROUP BY column;

Read GROUP BY Director as: sort the rows into one pile per director, then run the aggregate on each pile. Fourteen films by seven directors becomes seven rows.

The rule people break first

Every column in the SELECT list must either be in the GROUP BY or inside an aggregate. Asking for SELECT Director, Title, COUNT(*) ... GROUP BY Director is asking which of the five Lasseter titles should represent the pile, and there is no answer. Postgres and SQL Server reject it; SQLite and older MySQL pick one at random and tell you nothing, which is worse.

Filtering the groups

WHERE cannot see an aggregate, because it runs before the grouping happens — there are no groups yet for it to test. is the same idea applied after.

The form

SELECT group_by_column, AGG_FUNC(column_expression) AS aggregate_result_alias
FROM mytable
WHERE condition
GROUP BY column
HAVING group_condition;

Which one to reach for
  • WHERE — a test on one row, before grouping. Only count the films after 2000.
  • HAVING — a test on one group, after aggregating. Only show directors with more than two films.

A query can have both, and often should. Filtering in WHERE first is also cheaper: fewer rows reach the grouping.

Sheet 08 · SQLBolt lesson 12

Order of execution

The order the database actually runs the clauses in, which is not the order you write them, and the three errors that explains.

The order you write is not the order it runs

A query is written starting at SELECT. It is executed starting at FROM. Almost every confusing error message in SQL comes from that gap, and once you can recite the real order most of them explain themselves.

RunsWhat happens there
1 · FROM and JOINThe tables are read and combined. This decides the full set of rows everything else works on, and it happens before any of your conditions are considered.
2 · WHERERows are tested one at a time and dropped if they fail. Can only see columns that exist in the tables — not aliases, not aggregates, because neither exists yet.
3 · GROUP BYThe surviving rows are collapsed into one row per distinct value of the grouped columns.
4 · HAVINGWhole groups are tested and dropped. This is the first point at which an aggregate exists to be tested.
5 · SELECTThe output columns are computed — expressions evaluated, aliases created. Aliases exist from here on and not before.
6 · DISTINCTDuplicate output rows are removed, working on the columns SELECT just produced.
7 · ORDER BYThe finished rows are sorted. It runs after SELECT, which is why ORDER BY can use a column alias and WHERE cannot.
8 · LIMIT and OFFSETThe slice is taken, last of all. This is why a LIMIT without an ORDER BY gives you arbitrary rows.
The order, as a word

FROM · WHERE · GROUP · HAVING · SELECT · DISTINCT · ORDER · LIMIT

Three errors it explains

Why each of these happens
  • "no such column: sales_millions" in a WHERE, when you plainly defined that alias two lines up. WHERE runs at step 2 and the alias is not created until step 5. Repeat the expression, or wrap the whole query in another one.
  • "misuse of aggregate function COUNT()" in a WHERE. There are no groups at step 2. That test belongs in HAVING.
  • A LEFT JOIN that behaves like an inner one. The join happens at step 1 and keeps the unmatched rows with nulls in them; a WHERE at step 2 on a column from the joined table then throws every one of those rows away again.

What to do with it

Read an unfamiliar query in execution order rather than top to bottom: which tables, which rows, grouped how, then what comes out. A query that is hard to follow written down is usually straightforward in the order it actually runs.

Sheet 09 · SQLBolt lessons 13 to 15

Changing data

INSERT, UPDATE and DELETE — the half of the language that can destroy work in one line.

The other half of the language

Everything up to here reads. Nothing you have written could damage anything. The three statements on this sheet write, and two of them can destroy work in a single line with no confirmation and no undo.

Before you run one of these anywhere real

Write the WHERE first, as a SELECT, and look at what comes back. Those are exactly the rows you are about to change. Only then turn it into an UPDATE or a DELETE. A statement whose WHERE is wrong does not fail — it succeeds, on the wrong rows.

INSERT

The form

INSERT INTO mytable
(column, another_column, …)
VALUES (value_or_expr, another_value_or_expr, …),
      (value_or_expr_2, another_value_or_expr_2, …);

The column list is optional if you supply every column in the table's own order. Leaving it out is a habit worth not forming: the day somebody adds a column, every insert written that way breaks, and it breaks in production rather than at the point the column was added.

Several rows go in one statement, separated by commas, and that is much faster than one statement each. Values may be expressions, so VALUES ('Cars 3', 2017, 100 + 2) is fine.

UPDATE

The form

UPDATE mytable
SET column = value_or_expr,
    other_column = another_value_or_expr
WHERE condition;

Several columns in one SET, separated by commas. The new value can be built from the old one, and it is read per row before anything is written, so SET price = price * 1.1 does what you would hope.

An UPDATE with no WHERE

updates every row in the table. It is valid SQL, it will not warn you, and it is the single most expensive typo in this pack.

DELETE

The form

DELETE FROM mytable
WHERE condition;

Same shape and the same warning: DELETE FROM mytable; empties the table. There is no column list — a delete takes whole rows. To empty one column, that is an UPDATE setting it to NULL.

What professionals actually do

Four habits
  • Select it first. Same WHERE, as a SELECT *. Look at the rows. Then change the verb.
  • Take a backup of anything you cannot rebuild, before you touch it.
  • Use a where the engine has one: BEGIN, run it, look, then COMMIT or ROLLBACK. Everything up to COMMIT is reversible.
  • Test on a copy. Never let the first run of a destructive statement be against live data.

In the lab on this site none of that matters — Reset data puts the tables back. That is the point of practising here rather than at work.

Sheet 10 · SQLBolt lessons 16 to 18

Changing tables

CREATE TABLE, ALTER TABLE and DROP TABLE.

Changing the shape rather than the contents

The last three statements act on the table itself. Together with INSERT, UPDATE and DELETE from the previous sheet they are the whole write half of SQL.

CREATE TABLE

The form

CREATE TABLE IF NOT EXISTS mytable (
    column DataType TableConstraint DEFAULT default_value,
    another_column DataType TableConstraint DEFAULT default_value
);

IF NOT EXISTS makes the statement safe to run twice, which matters the moment it lives in a script.

TypeWhat it holds
INTEGER, BOOLEANWhole numbers. SQLite has no separate boolean — it stores 0 and 1.
FLOAT, DOUBLE, REALNumbers with a fractional part, held approximately. Never use one for money; use an integer count of pence, or a decimal type where the engine has one.
CHARACTER(n), VARCHAR(n), TEXTText. CHARACTER(n) is padded to a fixed length, VARCHAR(n) is capped at one, TEXT is unbounded.
DATE, DATETIMEA point in time. Storage and formatting differ between engines more than any other type.
BLOBRaw bytes. The engine does not look inside.

Constraints are the rules the table enforces on your behalf, which is a better place for them than in every program that writes to it: PRIMARY KEY, AUTOINCREMENT, UNIQUE, NOT NULL, CHECK (…), and FOREIGN KEY (col) REFERENCES other(col).

ALTER TABLE

The forms

ALTER TABLE mytable ADD column DataType DEFAULT default_value;
ALTER TABLE mytable DROP column;
ALTER TABLE mytable RENAME TO new_name;

Adding a column fills it with the default in every existing row, or with NULL if there is none. What an ALTER is allowed to do varies more between engines than anything else on this sheet — SQLite supports very little of it, and the standard workaround is to build a new table, copy the rows across and rename.

DROP TABLE

The form

DROP TABLE IF EXISTS mytable;

This one has no undo

DROP TABLE removes the table and everything in it. Not the rows — the table. There is no confirmation, and unless somebody took a backup it is gone.

Three that get confused

DELETE FROM t WHERE … removes some rows. DELETE FROM t removes all the rows and leaves the table. DROP TABLE t removes the table itself. Only the first is routine.

If another table has a foreign key pointing at this one, dropping it leaves those references pointing at nothing. Either drop them in dependency order, or declare what should happen with ON DELETE when the tables are created.

Sheet 11 · SQLBolt subqueries, unions

Beyond the basics

Subqueries, and UNION, INTERSECT and EXCEPT.

A query inside a query

Because a query returns a table, a query can be used anywhere a table or a value is expected. That is a , and it is what you reach for when the answer depends on another answer.

Three places it can sit, in rough order of how often you will write them:

PositionWhat it must return
In WHERE, against = or >A single value. WHERE Rating > (SELECT AVG(Rating) FROM boxoffice) is the shape you will use most: compare each row against a number derived from the whole table.
In WHERE, against INA single column, any number of rows. WHERE Id IN (SELECT Movie_id FROM boxoffice WHERE Rating > 8).
In FROMA whole table, which then needs a name: FROM (SELECT …) AS t. This is how you filter on an alias that WHERE could not see — compute it in the inner query, filter in the outer one.
Correlated or not

A subquery that mentions no column from the outer query runs once, for the whole statement. One that references the outer row — a correlated subquery — runs once per row of the outer query. The first is usually fine; the second is where a report that ran in a second starts taking a minute.

Stacking results

Set operators combine two result sets top to bottom rather than side to side. Both sides must have the same number of columns, in compatible types — the column names come from the first.

OperatorWhat comes back
Rows in either, with duplicates removed. The de-duplication costs a sort, so it is not free.
UNION ALLRows in either, duplicates kept. Faster, and the right one whenever you know there are no duplicates or you want to count them.
INTERSECTOnly rows in both.
EXCEPTRows in the first that are not in the second. MINUS in Oracle. Order matters — A EXCEPT B is not B EXCEPT A.
Join or union?
  • A join puts two tables side by side, adding columns. Use it when the two tables hold different facts about the same things.
  • A union stacks them one above the other, adding rows. Use it when they hold the same kind of thing in two places — this year's orders and last year's.

One ORDER BY at the very end applies to the whole combined result, not to either half.

Sheet 13

Glossary

Every term with a card on any sheet, in one alphabet.

Aggregate functiondefinition

One that takes a whole set of rows and returns a single value about them — a count, a total, an average.

In the proper languageA function computing one value over a group of rows: COUNT, SUM, AVG, MIN, MAX. All of them except COUNT(*) ignore NULLs entirely.

Aliasdefinition

A short name given to a table or a column for the rest of the query. AS is optional.

In the proper languageA temporary name bound to a table or a select-list expression. A column alias is visible to ORDER BY but not to WHERE, because WHERE runs before the select list is computed.

BETWEENtechnique

Tests whether a value falls in a range, including both ends. BETWEEN 2 AND 5 matches 2 and matches 5.

In the proper languageAn inclusive range predicate. Equivalent to x >= lo AND x <= hi.

Cardinalitydefinition

How many distinct values a column holds. A column with five is worth grouping by; one with a different value in every row is not.

In the proper languageThe number of distinct values in a column, or the number of rows in a relation. Drives whether an index helps and whether a GROUP BY has meaningful groups.

Clausedefinition

A keyword plus whatever belongs to it. A query is a stack of them, and they go in a fixed order.

In the proper languageA syntactic component of a statement introduced by a keyword — SELECT, FROM, WHERE, GROUP BY, HAVING, ORDER BY, LIMIT — which must appear in that order.

Columndefinition

One fact recorded about every row, holding the same type of value all the way down.

In the proper languageA named, typed attribute of a table. Every row carries a value for it, or NULL where no value is known. Also called a field.

Data warehouseconcept

A separate database built for asking questions rather than for running the business, so a heavy report cannot slow down the live system.

In the proper languageA consolidated analytical store, modelled for query performance rather than transactional integrity, fed from operational systems.

Databaseconcept

An organised store of information that more than one program can read and write at the same time without them treading on each other.

In the proper languageA structured, persistent collection of data managed by a database management system, which handles storage, retrieval, concurrent access and integrity.

DDLdefinition

The statements that change the shape of the database rather than its contents. Data Definition Language. CREATE, ALTER, DROP.

In the proper languageData Definition Language: the subset of SQL defining and modifying schema objects.

DISTINCTtechnique

Duplicate rows. It compares the whole selected row, not each column separately, so two columns give you distinct pairs.

In the proper languageEliminates duplicate tuples from a result set, applied after the select list is computed.

DMLdefinition

The statements that change what is in the tables. Data Manipulation Language. INSERT, UPDATE, DELETE.

In the proper languageData Manipulation Language: the subset of SQL that reads and modifies the rows held in existing tables.

ETLprocess

Moving data from where it is produced to where it is analysed. Extract, Transform, Load.

In the proper languageExtract, Transform, Load: the pipeline that pulls data from source systems, reshapes it and writes it into a warehouse. ELT loads first and transforms in place.

Foreign keydefinition

A column in one table holding values that belong to another table's key. That shared value is the entire link between the two.

In the proper languageA column, or combination of columns, in one table whose values reference the primary key of another table, constraining the referencing rows to match an existing referenced row.

FROMtechnique

Names the table the rows are coming out of.

In the proper languageThe clause naming the source of the rows a query operates on: a table, a view, a join of several tables, or a subquery.

GROUP BYtechnique

Sorts the rows into one pile per distinct value and runs the aggregate on each pile, giving one row per pile.

In the proper languagePartitions rows into groups by the listed expressions. Every select-list column must be grouped or aggregated; engines differ on whether breaking that is an error or silently returns an arbitrary row.

HAVINGtechnique

Filters whole groups after aggregating. WHERE cannot see an aggregate because it runs before there are any groups.

In the proper languageA predicate applied to groups after GROUP BY, the first point at which an aggregate exists to be tested.

Identifierdefinition

The name of something in the database rather than a word of the language — a table, a column.

In the proper languageA name referring to a database object. Case-insensitive in SQLite and MySQL; case-sensitive when quoted in PostgreSQL. Quoted with double quotes where it collides with a keyword or contains spaces.

INtechnique

Matches any value in a list. Shorter than a row of ORs and easier to read.

In the proper languageA membership predicate over an explicit list or a subquery returning a single column.

Indexconcept

A lookup structure that makes finding rows fast without reading the whole table. It costs disk, and it makes every write slower.

In the proper languageAn auxiliary structure, usually a B-tree, over one or more columns. Wrapping an indexed column in an expression usually stops the index being used.

INNER JOINtechnique

Any row without a match on the other side, from either table — silently, with nothing to tell you rows went missing.

In the proper languageReturns only the combinations satisfying the join predicate. The default when JOIN is written alone.

Joinconcept

Reading two tables as one wider table, matching rows by a value they both hold.

In the proper languageAn operation combining rows from two relations on a predicate, producing a relation over the union of their attributes.

Keyworddefinition

A word the language has reserved for itself, like SELECT or FROM. Capitals are convention, not a rule.

In the proper languageA reserved word forming part of SQL syntax. Case-insensitive; conventionally upper-cased to distinguish it from identifiers.

LEFT JOINtechnique

Every row of the first table whether it matched or not, filling the second table's columns with NULL where it did not.

In the proper languageAn outer join preserving all rows of the left relation, padding unmatched right-hand attributes with NULL. OUTER is optional and means nothing.

LIKEtechnique

Matches text against a pattern rather than exactly. % stands for any run of characters, _ for exactly one.

In the proper languagePattern-matching comparison for character data. Case-insensitive in SQLite and MySQL, case-sensitive in PostgreSQL, which is a real portability trap.

LIMITtechnique

Caps how many rows come back, applied last, after the sort. OFFSET skips that many first.

In the proper languageRestricts the result to at most n rows, evaluated after ORDER BY. TOP in SQL Server, FETCH FIRST in the standard.

Normalisationconcept

Splitting data so each fact is stored in exactly one place. It stops two rows disagreeing; the price is that answering a question now needs a join.

In the proper languageOrganising relations to reduce redundancy and update anomalies, by decomposing them so every non-key attribute depends on the key.

NULLdefinition

The absence of a value, not a value. It does not mean zero and it does not mean an empty piece of text — it means nobody knows.

In the proper languageA marker indicating that a value is unknown or not applicable. It is not equal to anything, including another NULL, so it is tested with IS NULL rather than with = .

ONtechnique

ON says how the two tables are matched; WHERE says which of the resulting rows you keep. On an outer join those are very different things.

In the proper languageThe join predicate. Applied during the join, before the WHERE clause filters the joined result — which is why a WHERE on the right-hand table turns an outer join back into an inner one.

ORDER BYtechnique

Sorts the result. Without it the order is not guaranteed — it will look stable right up until the day it is not.

In the proper languageSorts the result set on one or more expressions, ascending by default. The only construct that makes row order meaningful.

Primary keydefinition

The column whose value is different in every single row, so quoting the value picks out exactly one row and never two.

In the proper languageA column, or combination of columns, whose value uniquely identifies each row in a table. It cannot be NULL and cannot repeat. A table has at most one.

Projectionconcept

Choosing which columns come back. Choosing which rows come back is selection, and is done with WHERE.

In the proper languageThe relational operation that returns a relation over a subset of the original attributes. Distinct from selection, which restricts the set of tuples. SQL confusingly spells projection SELECT.

Querydefinition

A question put to the database. It reads and returns; it does not alter what is stored.

In the proper languageA SELECT statement: a request that returns a result set derived from one or more tables, without modifying the stored data.

RDBMSsoftware

The program that actually holds the tables and answers your SQL. Relational Database Management System. PostgreSQL, MySQL, SQL Server, Oracle and SQLite are all one.

In the proper languageRelational Database Management System: the software implementing the relational model — storage, transactions, concurrency, integrity constraints and a SQL interface over them.

Relational databaseconcept

A database that stores everything as tables that can point at each other, rather than as one big document or one long list.

In the proper languageA database organised as a set of relations (tables) of tuples (rows) over attributes (columns), where relationships between tables are expressed by shared key values rather than by stored pointers.

Result setdefinition

What comes back from a query. It is itself a table, built on the spot and thrown away, which is why a query can be fed into another query.

In the proper languageThe table of rows and columns produced by a query. It is not stored, is not named, and exists only for the life of the statement unless captured.

Rowdefinition

One of the things the table is about. One film, one customer, one order.

In the proper languageA single record in a table; one tuple, holding one value for each of the table's columns. Also called a record.

Schemadefinition

The shape of the database rather than what is in it: which tables exist, which columns each one has, and what type each column holds.

In the proper languageThe definition of a database's structure — its tables, columns, data types, keys and constraints — as distinct from the data held within it.

SELECTtechnique

Names the columns you want back. It narrows the table sideways — fewer columns, every row still there.

In the proper languageThe clause that specifies the projection: which columns, expressions or aggregates make up each row of the result set, and in what order they appear.

SELECT *technique

Returns every column, in the table's own order. Right for looking at a table you do not know; wrong for anything you intend to keep, because it silently changes shape when the table does.

In the proper languageThe wildcard projection, expanding to all columns of the source in their declared order. It is resolved at execution, so a column added later is picked up without the query changing.

SQLdefinition

The language you type at a relational database to ask it questions or change what it holds. Structured Query Language. You say what you want, not how to fetch it.

In the proper languageStructured Query Language: the standard declarative language for defining, querying and manipulating data in a relational database management system.

SQL injectionconcept

What happens when text a user typed is glued into a query as though it were code. The fix is parameters, never string concatenation.

In the proper languageAn attack where untrusted input alters the structure of a statement. Prevented by parameterised queries, which send values separately from the statement text.

SQLitesoftware

A small database engine that lives inside whatever program is using it, rather than running as a server you connect to. It is what the sandbox on this site runs.

In the proper languageAn embedded, serverless, zero-configuration SQL database engine storing an entire database in a single file. The most widely deployed database engine in the world.

Statementdefinition

One complete instruction to the database. The semicolon is what says it has finished.

In the proper languageA single executable SQL instruction, terminated by a semicolon. The terminator is what allows several statements to be submitted together.

Subqueryconcept

A query inside another query. Because a query returns a table, it can go anywhere a table or a value is expected.

In the proper languageA nested SELECT used as a scalar, a column, or a derived table. A correlated subquery references the outer row and runs once per row of the outer query, which is where a fast report becomes a slow one.

Tabledefinition

A grid holding one kind of thing. Every row is one of them, every column is one fact about all of them.

In the proper languageA named relation: a set of rows sharing a fixed set of typed columns. Also called a relation.

Transactionconcept

A group of changes treated as one. Either all of them happen or none of them do, and until you commit you can still take it all back.

In the proper languageA unit of work with atomicity, consistency, isolation and durability. Bounded by BEGIN and either COMMIT or ROLLBACK.

UNIONtechnique

Stacks two results one above the other, adding rows. A join puts two tables side by side, adding columns.

In the proper languageA set operator combining two result sets of matching arity and compatible types, removing duplicates. UNION ALL keeps them and is faster.

Viewdefinition

A saved query you can select from as though it were a table. Nothing is stored; it runs when you use it.

In the proper languageA named query whose result behaves as a relation. A materialised view does store its result and needs refreshing.

WHEREtechnique

Chooses which rows come back. It is tested against every row on its own, and the row survives if the test is true.

In the proper languageThe clause restricting the rows a query operates on, evaluated per row after FROM and before any grouping.
